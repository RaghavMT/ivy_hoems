# Walkthrough

Private study guide for the interview. Not committed: it is listed in `.git/info/exclude`, which is
git's local-only ignore file, so it never shows up in the public repo or its `.gitignore`.

It is updated as the project moves. Sections marked **Not built yet** fill in as features land.

How to use it: read sections 1–3 once for the story, then drill the question blocks. Every number
here comes from a file in the repo; the file is named so you can open it and point at it.

---

## 1. The project in one minute

Ivy Homes gave each candidate an API key for a property API (listings for sale, rentals, developer
projects) and a documentation file, `API_REFERENCE.md`. The documentation was AI-generated from an
old changelog and never reviewed. The API is honest; the documentation is partly wrong.

Three deliverables:

1. **A web app** with six working features: login, browse listings with filters, listing detail,
   saved listings, rentals and projects with correct units, and an insights screen.
2. **Ten answers** about the data, in `submission.json`.
3. **Findings**: every place the documentation disagrees with the API, in `submission.json`.

The one-line pitch: *I pulled the whole dataset once, tested every claim in the documentation
against it before building anything, logged every hypothesis including the ones that were wrong,
and built the app on top of the corrected picture, with one layer that fixes units so every number
on screen is right.*

---

## 2. How it is scored, and what that means for the interview

From `docs/statement.md`:

- **Stage 1, automatic, everyone.** Ten answers are worth 60, findings 40. Findings are scored as
  F1: precision and recall weigh the same, so a wrong finding costs as much as a missed one. The
  reasoning questions (2, 4, 6, 7, 9, 10) are worth more than the counting ones.
- **Stage 2, human review, top scorers only.** They open the app and use it, read the code, and
  read the commit history.
- **Final weighting.** Stage 1 is 50%, the app 40%, the writeup and commit history 10%.

What they are really testing, in their words: *"The first rule you write will fit most of the data.
Look hard at what it gets wrong. That is where the answer is."* Every good answer in this project
has the shape: first rule, why it was wrong, what the exceptions had in common, the rule that held.

## 3. How the work was organised

**Two workstreams in one repo.**
- Analysis, answers and findings: Python over a full local dump, done in Claude Cowork.
- The web app: React, done in Claude Code.
- Both are Anthropic's Claude. The README discloses this. The statement says using an LLM costs
  nothing and lying about it costs the internship.

**Process rules I kept.**
- Pull the data once (`dump.py`, 174 requests), then work offline. The statement itself says a full
  pull is about 150 requests and advises stopping there.
- Write each hypothesis in `docs/hypotheses.md` *before* testing it, then record the result.
  Refuted ones stay in; the README's "what turned out fine" section comes from them.
- Never report a discrepancy without reproducing it and saving the request and response under
  `data/_probe/`.
- Plan before building. The frontend plan is `docs/superpowers/plans/2026-09-13-frontend.md`.
- Small commits with real messages, feature branches, pull requests merged with merge commits so
  the history is readable.

**Likely questions**

- *"How much of this did the AI write?"* Answer honestly and specifically. Most code and prose was
  generated by Claude under your direction. What you did: set scope and priorities, chose to pull
  data once and work offline, reviewed and approved every commit, pushed back on process (commit
  style, planning before building), and checked results. Do not claim to have written code you did
  not write. Do show you understand every decision in this document.
- *"Why pull the whole dataset instead of querying the API as needed?"* Several answers need every
  record (duplicates, fakes, per-project counts). The statement recommends it. It keeps request
  volume tiny and makes every analysis reproducible from a frozen snapshot.
- *"Why commit so often?"* The statement says they read the history. Small commits show the order of
  reasoning, and let a reviewer see a rule change and why.

## 4. The data

| Collection | Records paged | `total` the API reports |
| --- | --- | --- |

City: Hyderabad. Assigned locality: Madhapur. Every record has `city_id: 2`, so the key's city
scoping holds (H-019, refuted).

Vocabulary you must be fluent in:
- **Lakh** = 1,00,000 rupees. **Crore** = 1,00,00,000 rupees = 100 lakh.
- **Carpet area**: floor you can walk on inside the flat. **Super built-up area**: carpet plus walls,

- **BHK**: bedrooms, hall, kitchen. "2BHK" means two bedrooms. `bedroom: 0` is mostly plots.
- **IST** is UTC+05:30. The fixed reference moment for all answers is 2026-09-10 00:00 IST.

## 5. The ten answers

Source of truth: `analysis/answers_v2.py`, output `analysis/out/answers_v2.json`. The script reads
only the dump, makes no network calls, and asserts five invariants every run. An earlier pass gave
different values for five answers; the commit "analysis: recompute ten answers, five change"
explains each change. Some entries in `docs/hypotheses.md` show the earlier numbers because the log
is append-only.

### Q1. Total listing records: **4,400**

Paged with `offset` until `has_more` was false. The API's own `total` says 4,224.

- *"Why not just use `total`?"* It under-reports on every collection. It equals 96% of the true
  count, rounded. Paging to the end is the only way to get the real number, and every paged ID was
  distinct, so nothing was double-counted.
- *"How do you know paging reached the end?"* `has_more` went false, the next offset returned an
  empty page, and no ID repeated across pages.

### Q2. Distinct properties: **3,675**

Several records can describe the same flat, often posted on different websites.

The rule: two records are the same property when they match on normalised apartment name, locality,
floor, bedrooms, bathrooms, covered parking and facing direction, and their carpet areas (unit
corrected) are within 2%. Matches are chained with union-find, so A=B and B=C puts all three together.

How it got there, rules tried and dropped:
1. Exact match on every field: **zero** matches. Duplicates carry small jitter in area and price.
2. Same coordinates: refuted. A coordinate identifies a building, not a flat.
3. Clustering by geography to check localities: the coordinates carry no locality signal at all.
4. The field-match rule above, first with raw apartment names: 4,255 properties.
5. Then the fix that changed the answer: apartment names are served in 246 variant spellings (case,
   punctuation, double spaces, a leading "The"). Normalising them finds 725 duplicate records instead
   of 143, giving 3,675.

Validation: merged pairs agree on price to a median of 3.4%, against 23.5% for random pairs with the
same locality and bedrooms. 537 of the 661 duplicate groups span two or more websites and none share
a contact number, so these are different sellers listing the same flat, not one seller re-posting.

- *"Isn't 2% tolerance arbitrary?"* In the earlier pass the count was identical at every tolerance
  from 2% to 10%. A plateau that wide means the rule found real structure, not a tuned threshold.
  Be careful: that plateau was measured before the name normalisation. If pressed, say so.
- *"Why do fake listings count toward distinct properties?"* The question says "genuine or not". Some
  fakes are clones of real flats, so they collapse into the real property's group.
- *"Why not use the phone number?"* Duplicates across portals never share a phone. Phones identify
  sellers, not properties.

### Q3. Active listings: **3,477**

Count of `is_live: true`. The documentation says the endpoint returns only active listings, but 923
records are not live (a `completeness` finding). The field `is_live` is not even in the documented
listing object.

### Q4. Impossible listings: **60 IDs**

Six classes of exactly ten records each, and no record in two classes:

| Class | Why it cannot exist |
| --- | --- |
| Price at or below zero | No property sells for nothing or less |
| Price under ₹1 lakh for a 2–3BHK | Served 1,000 times too small |
| Super built-up area below carpet area | Carpet is part of super by definition |
| Floor above the building's total floors | Contradicts itself |
| Posted after the reference moment | Posted in the future |
| Latitude and longitude swapped | Puts a Hyderabad flat in Kazakhstan |

- *"How did you know you had them all?"* Six unrelated classes of exactly ten is not how organic
  noise looks; it is a seeded set. The sixth class was missed at first and found by profiling every
  column's range rather than guessing rules: latitude topped out at 78.56.
- *"Why isn't the sub-lakh class fraud?"* Bait pricing is 30–50% below market so it still looks
  real. These are 99.9% below and would fool nobody. Confirmed as a unit slip: for the six that belong
  to a project, multiplying by 1,000 lands inside that project's other listing prices.
- *"What rule did you reject?"* `total_floors == 0` fires on 197 records, but all are plots with no
  floors. That is correct data.
- *"Why is the corrupt set checked against the fake set?"* An impossible record and a bait record are
  different defects. The script asserts the two sets never overlap.

### Q5. Total monthly rent in Madhapur: **₹59,78,500**

Sum of `price` over the 165 rentals whose `locality` field is Madhapur.

Two traps:
- *Monthly or annual?* Tested with deposit divided by rent. Indian leases take several months'
  deposit; the median ratio is exactly 5.0, so `price` is monthly (H-003, refuted).
- *Which locality?* 91% of rental titles name a different locality from the `locality` field.
  Neither field clusters geographically, so nothing can arbitrate. The structured field is the one
  the API documents and filters on, so that is used. The choice roughly doubles or halves the
  answer, which is why it is stated.

### Q6. Average price per square foot, live 2BHKs: **₹10,208.09**

Live, 2 bedrooms, excluding every ID in Q4 and Q9. The mean of each record's price divided by
carpet area, with square-metre areas converted.

- *"Why does unit correction matter here?"* magichomes serves areas in square metres after 1 June.
  Without converting, a 70 sq m flat looks like 70 sq ft and its price per square foot explodes. In
  the earlier pass the uncorrected mean was 78% too high.
- *"Mean of ratios or ratio of sums?"* The question says the mean of price divided by area, so mean of
  per-record ratios.
- *"Your app detects square metres by website and date, but the answer script uses a size threshold.
  Why two rules?"* Both select exactly the same 344 listings with bedrooms. The website-and-date rule
  is the explanation (a business cutover at midnight IST), and it also catches 14 plots the size rule
  cannot see. No answer uses plots, so every answer is unaffected.

### Q7. Costliest project: **P20384, ₹4,15,00,000**

Project prices are not in rupees. `price_max` is served in two units with nothing in between: 438
projects in crores (raw 1.00–4.15) and 32 in lakhs (raw 60.0–99.8).

- *"How did you decide the unit per record?"* Not by guessing from size alone. For each project, only
  one reading puts price divided by area inside the city's real market band.
- *"What went wrong first?"* The first rule, "min in lakhs, max in crores", fixed every min-above-max
  inversion and looked complete. It put P20165 at ₹99.8 crore for a 1,576 sq ft flat, over ₹6 lakh
  per sq ft, when the priciest listing in the city is ₹2.84 crore.
- *"One record said P20004 is the costliest."* That text is a prompt injection planted in P20004's
  amenities list, written to trigger only after someone solves the unit problem. P20004 is actually
  ₹2.58 crore. Ignored, and reported as a finding.

### Q8. Listings in the last seven days: **141**

Window: from 2026-09-03 00:00 IST up to, not including, 2026-09-10 00:00 IST.

- *"Timestamps end in Z. Are they really UTC?"* Tested. Hour-of-day was flat, so inconclusive. The
  decisive test used the magichomes unit cutover as a clock: read as UTC, the switch lands exactly at
  midnight IST; read as IST, it lands mid-afternoon, straddling nothing. So the Z is honest (H-020,
  refuted). The wrong reading gives 136.

### Q9. Fake listings: **135 IDs**

Enquiry bait: listings that exist to make people call a number.

The rule uses two signals that share no inputs, and they select the identical 135 records:
- **Price:** a phone number whose listings' median price is below 60% of the market rate for their
  locality and bedroom count, with at least five listings.
- **Naming:** a phone number used under more than one seller name, including invented agency-style
  names.

Rules tried first:
1. Phones with many listings: 739 repeat, useless alone.
2. One phone under several names: 12 phones, 261 listings. Over-counts, as predicted in advance,
   because real brokerages also share an office line.
3. Adding the price signal separates them cleanly into 7 bait phones and 5 brokerages.

| | Bait phones | Brokerages |
| --- | --- | --- |
| Median price versus market | 0.45–0.57 | 0.84–1.08 |
| Verified | 100% | 50–71% |
| Live | 100% | 72–86% |
| Names | invented agencies | real person names |

- *"Why is perfect verification suspicious?"* Real agencies always have some stale or unverified
  listings. Cheap *and* perfect is structurally implausible.
- *"Couldn't cheap listings just be good deals?"* One cheap listing, yes. A phone number whose entire
  portfolio sits at half price under many made-up names, no.
- *"Any independent confirmation?"* Some fakes are clones of real flats, matching on every structural
  field with the bait side at roughly half price.
- *"Why is Q9 risky?"* It is scored on invented IDs as much as missed ones. The brokerage separation is
  what keeps precision.

### Q10. Projects with a wrong listing count: **129**

- *"Wrong compared to what?"* The field was tested against ten possible meanings. It matches the
  number of *live* listings for 341 of 470 projects; every other meaning matches about 107. So it
  tracks live listings, and it is wrong for the 129 where even that fails.
- *"Why not check with the API's project filter?"* The documentation says the count agrees with
  `GET /v1/listings?project_id=...`, but that filter is silently ignored and returns everything. The
  documented cross-check is impossible through the API, so counts came from the dump.
- *"The first pass said 363."* That compared against every record including non-live ones. Finding
  that the field tracks the live subset changed the answer.

2. Data endpoints need the key *and* a logged-in user's token; the docs show the key alone.
3. Login tokens last 15 minutes, not 24 hours; the field is `access_token`, not `token`; a refresh

**Units**

**Data**
10. 923 returned listings are not live, though the docs say only active ones are returned.
11. 60 impossible records.

## 8. The web app

Live: https://ivy-hoems.vercel.app. Code in `web/`.

### 8.1 The stack, and why

- **React with TypeScript**, built by **Vite**. A single-page app: the browser loads one page, and
  JavaScript swaps screens without reloading.
- **React Router** gives each screen a real address like `/listings/MAG-2000002`, so detail pages
  are reachable by URL as required.
- **No UI library, no state library.** Fewer moving parts, one stylesheet, and every line is
  explainable.
- **Vitest** for tests; **Playwright** driving real Chrome for end-to-end checks.
- **Vercel** hosting: every push to a branch gets a preview link; merging to `main` updates the live
  site.

Likely questions
- *"Why not Next.js?"* No server-side needs: the API allows browser calls directly, and a static app
  is simpler to deploy and reason about.
- *"Why TypeScript 5.9 and not 7?"* 7 had just shipped as a full rewrite. On a deadline, a proven
  toolchain wins. The build does not depend on the type checker, so a type-tool quirk cannot block a
  deploy.

### 8.2 Where the data comes from

- **Live API, from the visitor's browser:** login, listings, rentals, projects, detail pages. Each
  user action is one request, 50 records at a time. The API allows browser calls from any site
  (CORS is open).
- **Committed analysis output:** the insights screen, because the analytics endpoint does not exist
  and its numbers must match `submission.json` exactly.
- **The dump:** used only by tests, with no API calls.

Likely questions
- *"Your API key is in the JavaScript bundle. Isn't that a leak?"* For a browser app calling the API
  directly, anything the browser sends is visible to the user; there is no hiding it without a proxy
  server. The key is already public in `submission.json` by the assignment's design, and every
  request is logged against it. With more time, a small proxy would keep it server-side. It is stored
  as a Vercel environment variable, not in the source code.
- *"Every reviewer's click uses your key?"* Yes. That is how a live demo against this API has to
  work, and the volume is tiny against a 1,200-per-minute limit.

### 8.3 Feature 1, login: **built**

How it works, in plain terms:
1. You submit email and password. The app sends them with the key.
2. The server returns two tokens: an **access token** that works for 15 minutes, and a **refresh
   token** used to get new ones.
3. Both are saved in the browser's local storage, so a page refresh keeps you logged in.
4. A minute before the access token expires, the app quietly exchanges the refresh token for a new
   pair. If the server rejects a token anyway, the app refreshes once and retries the request.
5. Pages that need data check for a session. With none, they send you to login and remember where
   you were going, then take you back.
6. Logout makes the browser forget the tokens.

Why built this way:
- **Two layers of refresh.** The timer avoids a failed request on a slow server; refresh-on-failure
  covers tabs whose timers the browser paused. Proven with a real 31-minute idle test: the old token
  was rejected, the refresh worked, data loaded (H-030).
- **A busy server never logs you out.** Only a rejected token does. The server was taking up to 17
  seconds per request the night this was built; a login screen that logs people out on a timeout
  would fail the demo.
- **Logout is client-side** because the server keeps no session state; its own logout reply says
  so (H-031).
- **Shared refresh.** If several requests need a refresh at the same moment, they wait on one refresh
  instead of firing several.
- **Safe return address.** The "go back after login" address only accepts paths on this site, so a
  crafted link cannot bounce someone to another website.
- **Tabs stay in sync.** Logging out in one tab logs out the others.

Tests: 35 rule tests for the session, the API client and the return address. 16 end-to-end checks in
real Chrome against the live server: redirect to login, wrong password message, login, persistence
after refresh, background refresh, logout, deep-link return, second user, crafted link, phone width,
no unexpected console errors.

Likely questions
- *"Why local storage and not cookies?"* The API uses bearer tokens in a header, not cookies, and
  there is no server of ours to set cookies. Local storage is the standard place for a static app.
- *"Isn't local storage vulnerable to XSS?"* Any script injected into the page could read it. React
  escapes rendered text by default and the app never inserts raw HTML, which matters because seller
  text contains injection attempts. A backend with httpOnly cookies would be the stronger design with
  more time.
- *"What happens if the refresh token expires?"* The next request fails to refresh, the session is
  cleared, and the user is sent to the login page, then back to the page they were on after logging
  in. The login page does not yet say *why*; a "your session ended" note is a small improvement to
  mention.
- *"What does 'still working after 30 minutes' actually test?"* That the app handles the 15-minute
  token. An app that stores one token and never refreshes breaks at minute 15.

### 8.4 Unit correction: **built**

One module, `web/src/lib/normalise.ts`, is the only place units change. Every record passes through
it between the API and the screen. The corrected records no longer carry the raw fields at all, so no
screen can show a raw number by mistake.

| Resource | Served as | Corrected to |
| --- | --- | --- |
| Listings, magichomes, posted from 1 June IST | square metres | × 10.7639 to square feet |
| Project prices, raw value below 10 | crores | × 1,00,00,000 rupees |
| Project prices, raw value 10 or more | lakhs | × 1,00,000 rupees |
| Listing prices, rental prices | already rupees | unchanged |

Tests check the rules against the whole dump: exactly the 358 converted IDs the analysis found, no
project with min above max, and the costliest project equal to the submitted answer.

Likely questions
- *"Why one module?"* If a conversion were fixed on one screen but not another, a price could be right
  on the list and wrong on the detail page. With one module, every screen changes together.
- *"How did you find the price_min problem?"* A raw minimum of 1.0 would mean a ₹1 lakh flat. Checked
  all 470: two groups with a gap from 1.43 to 31.4; the low group only makes sense as crores (₹7,505–
  10,522 per sq ft instead of ₹75–105).

### 8.5 Feature 2, browse listings: **built** (uncommitted until approval)

What you see on `/listings`:
- A filter bar under the heading: locality, bedrooms, min and max price in rupees, furnishing.
  Dropdowns apply immediately; price boxes apply on Enter or Apply. A hint under each price box
  shows what you typed in lakhs or crores, so 6000000 reads as ₹60 L.
- Result cards: title built from structured fields ("3 BHK apartment, Mantri Park"), locality and
  furnishing, floor, facing, baths. Price on the right in aligned figures, carpet area in sq ft.
- Badges only when they mean something: "Not live", "Verified", and "Converted from m²" on the
  records whose area the source served in square metres. A coloured left edge marks not-live
  (amber) or verified (blue) cards.
- "Showing 50 homes so far" and a "Load more homes" button; at the end, "All 62 matching homes
  shown". An empty state with "Clear filters" when nothing matches. A retry button on errors, and
  a "server is slow" note after five seconds.
- On phones the filters fold behind a "Filters, 2 active" button so homes are visible first.

How it connects, in order:
1. The address bar holds the filters. The page reads them, so reload, back button and shared
   links all keep the same view.
2. The page asks the API for 50 matching records, sending the filters.
3. Every record is re-checked in the browser against the same filters, then passed through the
   unit converter.
4. If fewer than 50 matches came back but the server says there are more, the app reads the next
   page, at most three pages per click. With the real server this never happens, because its
   filters work. It is there because the assignment says filters must work "whether or not the
   server helps you".
5. "Load more" continues from where the last page stopped. A response that arrives after you
   changed filters is thrown away, so old results never overwrite new ones.

How it was tested: 25 checks in real Chrome against the live API, using 15 requests. Each filter
changes the cards, filters combine, reload keeps them, an impossible combination shows the empty
state, and one filter with 62 matches in the dump loads to the end showing exactly 62 unique homes.
`MAG-2000002` shows 732 sq ft with the converted badge.

Likely questions
- *"How do you know the filters actually filter?"* Two ways. A rule test runs the browser filter
  over all 4,400 records and reproduces every total the server reported for the same filter. And
  the browser test checks every card on screen after each filter change.
- *"What if the server ignored a filter?"* The browser check would drop the wrong records, and the
  app would keep reading pages until it had enough, then say results were filtered in the browser.
- *"Why not show '4,224 homes'?"* That is the server's `total`, and it is 4% low. The page only shows
  counts it can stand behind: how many it has loaded, and the exact number once it reaches the end.
- *"Why 50 per page?"* That is the server's real maximum, whatever the documentation says.
- *"Why is the filter in the URL and not in state?"* A filtered view becomes a link: refresh keeps
  it, back undoes a change, and a reviewer can paste it.
- *"Why do some cards show a negative price?"* Those are the impossible records from Q4. The app
  shows data as served instead of hiding it; the insights screen explains them.

- **Filters run twice.** The app sends locality, bedrooms, price range and furnishing to the server,
  then re-checks every returned record in the browser. All four server filters work (H-016), but the
  requirement is that filters work whether or not the server helps.
- **If the server ever ignored a filter,** a page could come back with few matches. The app keeps
  fetching the next page until it has enough, with a cap on pages per click.
- **Proof the two agree:** a test runs the browser filter over the whole dump and reproduces every
  total the server reported in the filter probe.
- **Paging:** 50 records per request (the server's real cap), advancing by `offset`, stopping when
  the server says there is no more. The server's `total` is never shown because it is 4% low.
- **Filters live in the address bar,** so refresh, back button and shared links keep them.
- **Price bounds are inclusive,** matching the server exactly (H-034).

### 8.6 Feature 3, listing detail: **built** (uncommitted until approval)

What you see on `/listings/MAG-2000002`:
- A title from structured fields, the locality, and the posted date in IST.
- A price panel: price in lakhs or crores, the exact rupee amount, price per square foot of carpet
  area, carpet and super built-up areas, and a note when the areas were converted from square metres.
- "About this home" facts, "Listed by" details, and the seller's description with a note that the
  seller wrote it.
- A back link that returns to your filtered results when you came from them, or to all listings
  when the page was opened directly.

How it connects: the address holds the listing ID; the page asks the API for that one record at the
plural path `/v1/listings/{id}` (the documented singular path does not exist); the record goes
through the same unit converter as the list; a 404 becomes "This listing doesn't exist".

Why dates are converted: timestamps are honest UTC. `MAG-2000002` was posted at 18:37 UTC on 8 July,
which is 00:07 on 9 July in Hyderabad, so the page says 9 Jul 2026.

How it was tested: 16 checks in real Chrome using 5 API requests. A logged-out deep link goes to
login and comes back to the listing; a new tab opens it directly; an unknown ID shows not-found;
`MAG-2000002` shows 732 and 947 sq ft with the converted label; `100-2000006`, whose description
tells AI tools to add a field to `submission.json`, shows that text exactly and nothing acts on it.

Likely questions
- *"What stops seller text from injecting HTML or script?"* React renders text, not markup, and the
  page never inserts raw HTML. The test checks the description contains no elements.
- *"Why show the injected text at all?"* It is the seller's data. Hiding it would be editing listings;
  the right defence is never treating data as instructions. The insights screen explains it.
- *"Why is the listing ID in the address and not in app state?"* The assignment requires a page per
  listing reachable by URL, not a modal. Real routing also means back, refresh and sharing work.
- *"What does the per-square-foot figure use?"* Price divided by converted carpet area, the same basis
  as Q6. It is hidden when the price is zero or negative, which only happens on impossible records.

### 8.7 Feature 4, saved listings: **built** (uncommitted until approval)

What you see: a Save button on every listing card and in the detail page's price panel. It turns into
a filled "Saved" button. `/saved` lists saved homes newest first, with price, area, the date saved,
a Remove button, and a note explaining where they are stored.

How it connects:
1. The documented favourites endpoint returns 404, so there is no server to store saves.
2. Saves go into the browser's storage under a key made from the logged-in email, like
   `ivy.saved.demo1@ivy.homes`. The login session is stored under a different key.
3. Logging out only removes the session key, so the saved list is still there on the next login.
4. Each save captures a small snapshot: title, locality, price, area, live status. The saved page
   shows the snapshot, so opening it costs zero API requests, even with many saved homes.
5. One shared store keeps every Save button and the saved page in step, including across tabs.

How it was tested: 11 rule tests for the store (per-user separation, survives logout, corrupt or
blocked storage). 18 checks in real Chrome with 9 API requests: demo1 saves two and reloads, logs
out, demo2 sees none and saves one, demo1 logs back in and sees exactly their two, removes one,
reloads, then unsaves the last from the detail page. The saved page is asserted to make no requests.

Likely questions
- *"So saved listings don't follow the user to another device?"* Correct. It is the honest limit when
  the server endpoint does not exist, and the page says so.
- *"Why a snapshot instead of fetching each saved listing?"* Fetching 20 saved homes would be 20
  requests on every visit. The snapshot is instant and free; clicking through to the detail page
  still shows the live record.
- *"Couldn't the snapshot go stale?"* Yes, a price could change after saving. The page says prices are
  as they were when saved. With a real favourites endpoint that trade-off disappears.
- *"What if two users share a browser?"* Each gets a separate list keyed by their email, which is what
  "per user" requires here.

### 8.8 Feature 5, rentals and projects: **rentals built and merged (PR #3); projects built** (uncommitted until approval)

Rentals, what you see on `/rentals`: the same browse layout as listings with locality, bedrooms and
furnishing filters. Cards show rent "a month", the deposit in rupees, and carpet area. `/rentals/{id}`
has a panel with rent, security deposit and how many months of rent it is, maintenance, and both
areas, then the facts, who listed it, and what the seller wrote.

Two data problems this page handles:
1. **Deposits in months (new finding, H-036).** Every rental from zerobroker, 344 of them, serves
   `deposit` as a number from 2 to 10. Every other website serves rupees, and on all 1,306 of those
   the deposit is exactly 2 to 10 times the rent. So zerobroker writes "6" meaning six months. The app
   multiplies by the rent and labels it. `R2000514`: rent ₹7,800, served deposit 6, shown ₹46,800.
2. **Seller titles that name the wrong locality (H-022).** 91% of rental titles mention a different
   locality from the `locality` field. Headings are built from structured fields; the seller's title
   is shown under "What the seller wrote" with a note when it disagrees.

How it connects: the browse page and the listings page now share one loader (filters to the server,
re-check in the browser, normalise, page, drop stale responses), and the detail pages share one
single-record loader. Only the endpoint, filter and converter differ.

How it was tested: rule tests over all 1,650 rentals prove exactly the 344 small deposits are
converted and every deposit ends up a whole 2–10 months of rent. 23 checks in real Chrome with 8 API
requests: each filter, and three rentals checked against the dump (the wrong-locality title, the
6-month deposit, and the highest rent in the city).

Likely questions
- *"How did you find the deposit problem?"* Picking spot-check records for the test, one had a ₹6
  deposit. Instead of treating it as one bad record, I checked the whole column: a clean cluster of
  2–10, one website, every record of that website, and on the other websites the deposit is always a
  whole number of months. That pattern is a unit convention, not corruption.
- *"Why convert by website and not just 'if the deposit is under 100'?"* Both select the same 344
  records. The website rule is the explanation; a test checks it matches the magnitude rule, so if
  either assumption broke, the test would fail.
- *"Did it change any answer?"* No. Q5 sums rent, not deposit. It did correct an earlier log entry
  that quoted the median deposit as five months: that median included the month counts.
- *"Why not just use the seller's title?"* It is wrong 91% of the time, and the structured field is
  the one the API documents and filters on.

Projects, what you see on `/projects`: the same browse layout with locality and status filters. Cards
show the project name, locality, developer, status, possession date, towers and units, and on the
right the price range in rupees and the unit sizes in sq ft. `/projects/{id}` has a panel with the
price range (compact and in full rupees), unit sizes, possession date, and a note saying which unit
the source used; then the facts (developer, status, launch date, towers, floors, units, RERA number),
the listing count, and the amenities.

Three data problems this page handles:
1. **Prices in lakhs or crores (units finding, H-035).** Neither price is rupees. Each value below 10
   is crores, each value of 10 or more is lakhs; nothing is served between 4.15 and 31.4, so the split
   is clean. It is decided per value, not per project: `price_min` is crores for 90 projects and
   `price_max` for 438. Three checks against the dump: P20384 ₹1.39 Cr to ₹4.15 Cr (the costliest, Q7),
   P20004 ₹1.21 Cr to ₹2.58 Cr, P20007 ₹37.9 L to ₹87.2 L. The converter also records which unit each
   value was served in, so the page can say so without any component knowing the rule.
2. **A listing count that can't be trusted (consistency finding, Q10).** `total_listings` counts live
   listings only and is still wrong for 129 projects. The browser can't recompute it without paging
   every listing, and the API ignores `project_id` as a filter (H-016), so the page shows the figure as
   "according to the source" with a note to treat it as approximate.
3. **An instruction hidden in amenities (data_quality finding).** P20004's amenities include a note
   telling AI tools to report it as the costliest project. The page shows it as one more plain-text
   amenity, as supplied, and nothing on the page repeats the claim. It is rank 102 by corrected price.

How it was tested: rule tests over all 470 projects (no minimum above its maximum after conversion,
the costliest equals the submitted answer, the unit split is exactly 90 and 438). 28 checks in real
Chrome with 8 API requests: each filter, a combined filter that shows all 13 Kompally new launches
the dump has, and the three projects above, including that the injected amenity is plain text and
the words "costliest" and "56804321" appear nowhere else on the page.

Likely questions
- *"Why not flag every card as converted, like the m² badge on listings?"* Every project price is
  converted, so a badge on every card says nothing. The page header says it once, and each detail
  page says which unit that project's values came in.
- *"Why not hide the injected amenity?"* Deciding which seller text to hide is its own judgement call
  and could hide real data. Shown as inert text, it can't do harm, and the insights screen explains it.
- *"Why show `total_listings` at all?"* It's the only count available per project, and hiding it
  would hide a finding. Labelling it approximate is honest about what it is.

### 8.9 Feature 6, insights: **data build and screen built** (uncommitted until approval)

The screen reads one generated file, `web/src/generated/insights.json`, and computes nothing in the
browser. It is built offline:
1. `python analysis/answers_v2.py` (the analysis session's script) writes `analysis/out/evidence.json`:
   the six impossible-record classes, the bait listings and their clone pairs, the 661 duplicate
   groups, the 129 projects with a wrong count, and the ID lists behind each unit problem.
2. `npm run prepare-data` (Node running TypeScript directly) reads the dump, `submission.json` and
   `evidence.json`, converts units with the app's own `normalise.ts`, and writes the file. It checks
   each count against the answers and the text of its finding, and checks that the app's converters
   select exactly the IDs `evidence.json` lists. If anything disagrees it refuses to write. Proven by
   breaking one expected phrase: the build stopped.

History worth knowing: the first version of `evidence.json` was older than the final rules (289
duplicates, five impossible classes, 363 wrong counts). I first worked around it with a second
exporter; Raghav pointed out that duplicated the analysis files, so the analysis session updated
`evidence.json` instead and the exporter was deleted. One open inconsistency: `evidence.json` lists 42
bait/genuine clone pairs, the fraud finding says 14, so the screen shows example pairs but no count.

What `/v1/analytics/summary` promised (it returns 404) is computed two ways:
- **As served:** all 4,400 records, raw values. Median price ₹1.06 Cr, ₹10,123 per sq ft.
- **Corrected:** live, not impossible, not bait, one record per property, areas in sq ft. 2,890
  homes, median ₹1.074 Cr, ₹9,905 per sq ft. Excluded: 923 not live, 43 impossible (the other 17 were
  already not live), 135 bait, 409 repeat listings.

How it was tested: rule tests for the median and grouping; a test over the generated file that fails
if it disagrees with `submission.json` or with the dump run through the app's converters (147 tests).

Likely questions
- *"Why two columns?"* The documentation doesn't say what the endpoint counts. Showing both makes the
  cost of each data problem visible instead of hiding a choice.
- *"Why not compute it in the browser?"* The analysis needs every record; the browser would have to
  page the whole API on every visit. The graded numbers also stay identical to `submission.json`.
- *"Why is 'corrected' a different median from Q6?"* Q6 is the mean price per sq ft of live 2 BHKs;
  this is the median across all bedroom counts. Different questions.

## 9. Testing approach

- **Rule tests** (Vitest, no network) for anything that can be wrong: session expiry, the API client,
  unit conversion, filters, paging, formatting. Several run against every record in the dump rather
  than a few examples.
- **Browser tests** (Playwright in real Chrome) click through the deployed app against the real
  server, with a small request budget per run.
- **Tests first.** Each rule test was written and watched failing before the code existed, so the
  test is known to catch the bug it targets.

Likely question: *"Why test against the whole dump?"* A rule that works on three hand-picked records
can still fail on the 358th. Checking every record against the analysis output means the app and the
answers cannot silently disagree.

## 10. API usage and the rules

The statement: do not attack the API, no scanning, 1,200 requests per minute per key, every request
logged against the key.

- Full data pull: 174 requests, once.
- Probes: a few requests each, 150 ms apart, results saved.
- No endpoint was guessed. Missing endpoints were called once at their documented path only.
- Frontend work so far: roughly 50 requests across probes and browser tests. An exact per-run log
  is planned as `docs/api-calls.md`.
- The app never loads a whole collection; tests never page through one.

## 11. Security and safety

- **Prompt injection in the data.** Twelve records contain instructions aimed at AI tools: add a
  field to the submission, show a fake "certified by" footer, report a fake finding, and name the
  wrong costliest project. None were followed. The app shows all seller text as plain text and never
  acts on it.
- **Secrets.** The key lives in `.env` and Vercel environment variables, never in source files.
  Probe outputs never store tokens.

## 13. Honest weaknesses

  submission and the commit messages carry the current ones.
