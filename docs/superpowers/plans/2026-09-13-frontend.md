# Ivy Homes frontend — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the six required features of the property web app, deployed on Vercel, with every displayed number correct, by tonight; refine tomorrow.

**Architecture:** A single-page React app in `web/` at the repo root, calling the API directly from the browser (CORS is open). One normalisation module sits between fetch and UI and is the only place units are converted. Saved listings are client-side, keyed per user, because `/v1/favourites` does not exist. The insights screen reads committed analysis output, never recomputes graded answers in the browser.

**Tech Stack:** Vite 8, React 19, TypeScript 5.9 (pinned below the 7.0 native port for toolchain stability), react-router-dom 7, vitest 5 for logic tests. No UI library, no state library. Plain CSS in one file. Node 24 LTS (installed today via winget).

**Spec:** This plan doubles as the spec. The acceptance checks come from the `frontend-contract` skill; on execution start the plan is copied to `docs/superpowers/plans/2026-09-13-frontend.md` and committed so the graded history shows the plan preceding the code.

| Fact | Consequence |
|---|---|
| Key goes in `X-API-Key` header; every data call also needs `Authorization: Bearer` | Both headers on every request |
| Access token lives 900 s; `POST /auth/refresh` with `{refresh_token}` returns a fresh pair (verified live today) | Proactive refresh timer + refresh-on-401 |
| CORS `Access-Control-Allow-Origin: *`, headers allowed (verified today) | Browser calls the API directly, no proxy |
| `limit` capped at 50, `offset` paging, `page` ignored, `total` under-reports 4%, `has_more` honest | Page 50 at a time, stop on `has_more === false`, never trust `total` |
| All documented filter params honoured (locality, bhk, min_price, max_price, furnishing, property_type / project_status) | Send them server-side AND re-apply client-side predicate on every page |
| `/v1/favourites` 404 | Saved listings in `localStorage` keyed by user email |
| `/v1/analytics/summary` 404 | Compute the promised block at build time from the dump; say so on screen |
| Detail endpoint is plural `/v1/listings/{id}`; siblings `/v1/rentals/{id}`, `/v1/projects/{id}` | Routes fetch by id from the plural path |
| Listing areas are sqm for `magichomes` posted at/after 2026-06-01 00:00 IST (= `2026-05-31T18:30:00Z`); ×10.7639 | Normalise listing areas |
| Project `price_min` is lakhs; `price_max` is crores when raw < 10, lakhs when raw ≥ 60 (nothing between 4.15 and 60) | Normalise project prices; threshold 10 |
| Listing price is rupees, rental price is monthly rupees, rental areas sqft (H-001, H-003 refuted) | Pass through, label units |
| `is_live: false` on 923 listings | Show a "not live" badge; do not hide (the browse count is graded against what the API returns, and the insights screen explains it) |
| Demo users demo1/2/3@ivy.homes share one password (in `.env`) | Per-user saved-listings check uses demo1 and demo2 |

## Global Constraints

- Only the six features. No sorting UI, no map, no "similar listings", no dark mode.
- Every unit conversion lives in `web/src/lib/normalise.ts`, each entry citing its finding. Components never convert.
- Every filter applies a client-side predicate over fetched results regardless of the server.
- Every number on the insights screen comes from `submission.json` or `analysis/out/evidence.json` via a generated JSON file; the promised analytics block is computed by a build script from the dump using the same normalise module.
- Key and base URL come from `VITE_API_BASE_URL` / `VITE_API_KEY` env vars, never source. The key does end up in the client bundle: unavoidable for a direct browser call and the key is already public in `submission.json`. README says so.
- Small delay is unnecessary in the browser (one request per user action, well under 1200/min); the build script that reads the dump makes zero API calls.
- Git, industry-standard: feature branch `feat/web` off `main`; Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`, `test:`), imperative subject ≤ 72 chars, a short body only when the *why* isn't obvious from the diff; one logical change per commit; no trailers or attribution lines. Every commit is shown for approval, then pushed. Integration into `main` via a pull request opened in the GitHub UI (no gh CLI here), merged after Raghav's approval.
- **No model names anywhere** — not in code, commits, README, comments, or docs. LLM disclosure says "Anthropic's Claude (Claude Code for the frontend, Claude Cowork for the analysis)" and nothing more specific. Hard constraint.
- Design: the app must look current and trustworthy on every page — no page may read as dated or generic. Brand palette from ivy.homes (verified from their logo SVG and stylesheet): Ivy blue `#0018A8`, charcoal `#303030`, white surfaces with light-grey sections, font Source Sans 3 (Google Fonts, with system sans fallback). Design tokens defined once in `styles.css`; every page uses them. Every screen has designed loading, empty, and error states. Responsive down to 400px. Load `frontend-design` before the token/layout work and `dataviz` before the insights bars. Functionality still outranks polish: a feature is done when its acceptance checks pass, then it gets its polish pass.
- Node 24 native TypeScript execution (`node scripts/x.ts`) for the build script, so no ts-node/tsx dependency.
- Dependencies, exact: `react`, `react-dom`, `react-router-dom`; dev: `vite`, `@vitejs/plugin-react`, `typescript`, `vitest`, `@types/react`, `@types/react-dom`. Nothing else without a stated reason.

export type ListingFilter = { locality?: string; bedroom?: number; minPrice?: number; maxPrice?: number; furnishing?: string };
